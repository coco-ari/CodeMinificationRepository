# 工程与 AI 协作规范

与 [项目入口](../AGENTS.md)、[后端规范](backend-standard.md)、[T3 UI 规范](t3-ui-standard.md)共同约束当前分支的维护、模块优化与后续开发。这里只维护跨模块工程方法和前端代码组织，不重复业务字段与 UI 尺寸。

## 面向 AI 的开发流程

1. 先定位业务所有者、公开合同、调用链及现有测试；注明当前事实、目标规则和未决问题，不凭文件名或旧方案推断已实现能力。
2. 把任务拆成可运行的纵向切片：合同 → 应用/领域 → 持久化与权限 → 入口 → 必要界面 → 验收。每个切片有具体触发、结果、失败路径和退出条件。
3. 优先复用现有组件和成熟开源实现。抽象只为已经出现的共同规则服务；禁止为未来想象的模块建立通用 CRUD、万能仓储、工作流引擎或插件解释器。
4. 先确认接口与状态所有权再改调用方；一个值有一个权威来源。不要分别给 HTTP、MCP、页面和后台修出四份不同业务规则。
5. 新增行为用针对性测试保护关键不变量；修复缺陷先保留能复现真实错误的用例。低风险文案/样式不写只镜像实现的测试，采用相应可视或交互验收。
6. 遇到失败先判断是本次缺陷、基线失败还是环境限制；保留证据并修正原因。不能通过跳过测试、降低类型严格度、吞异常或加入假成功回退完成任务。
7. 交付说明行为变化、使用入口、验证结果与未覆盖项。普通任务不生成大型过程文档；跨会话只记录必要决策、剩余工作和可复现命令。

## 模块说明与依赖组织

每个实际模块只维护一份简短说明，可放在模块 README 或现有入口文档。写清下列内容，并链接代码合同及测试；不手抄每个字段，也不为未实现能力创建空模块。

| 项目 | 必须说清的内容 |
| --- | --- |
| 职责 | 本模块负责什么、不负责什么；当前功能入口及调用方 |
| 数据与状态 | 自有表、文件元数据、缓存及任务状态；引用其他模块的标识 |
| 公开能力 | 公开入口、输入输出合同、业务错误；内部文件不对外承诺 |
| 依赖 | 允许依赖的模块和具体用途；装配位置；同步调用或异步通知的理由 |
| 权限 | 动作标识、资源真实归属、私有/共享限制、撤权处理；链接同源动作合同与权限用例 |
| 运行与验证 | 配置、初始化/关闭、资源预算、失败影响范围；成功、越权与故障的验证入口 |

- 后端沿用现有 `autoops/server/modules/<模块>` 的公开入口模式；前端在当前 T3 宿主内按业务功能组织，不另建应用或页面壳。现有目录是否迁移，在第二步按调用关系确定，不一次批量搬动全仓。
- 模块内部按需要拆入口、用例、领域和基础设施；小模块可以少文件，不建立空层。文件划分依据职责与变化原因，不用固定行数迫使简单逻辑碎片化。
- 公共合同只含可共享的 Schema、DTO、动作与错误语义，不导入服务端运行时。前端不能导入服务端存储、凭证或执行器；后端不能依赖页面组件。
- 依赖方向为入口调用应用服务，应用服务使用领域规则及注入端口，基础设施实现端口，组合根负责装配。组合根不写业务规则，也不发展成万能路由/服务文件；入口按所属模块组织。
- 跨模块只使用公开能力；出现双向依赖时，先核对职责，把跨模块用例放到明确的协调位置，通过公开端口装配。不以动态导入、全局事件总线或服务定位器绕过边界检查。
- 平台共享层仅提供配置、连接、事务、日志等机制，不导入业务模块。一个模块独用的辅助代码留在本模块；提取共享代码须有真实调用者和共同语义，禁止以 `common/utils` 收纳难归属的业务逻辑。
- 发现循环必须消除，不因补写说明而获准保留；变更所有权时先更新依赖说明、合同及受影响调用方，再改实现。自动边界检查需包含类型导入、路径别名与新增目录；检查未覆盖的目录必须明确列出，不能声称全仓受控。

## 模块与合同

- 模块公开入口只导出明确服务、DTO 和注入端口，内部实现不成为隐式 API。依赖方向由自动检查约束；领域层不得依赖 HTTP、数据库驱动、前端或 T3 内部代码。
- 运行时输入校验与 TypeScript 类型同源；优先沿用 T3 已使用的 Effect Schema。公开 DTO 与数据库行分离，禁止把数据库对象、凭证明文或第三方完整响应直接返回客户端。
- 动作、错误码、资源身份和 API 合同在公共合同中定义；前后端不手抄枚举、重新解释角色或拼接隐藏协议。时间使用明确时区的时间戳，字节、持续时间等字段标明单位；金额等精确值不使用含糊浮点数。
- 输入使用允许字段集合，明确空值、缺省、长度、分页、排序和大小上限；未知资源与无权限按统一策略返回，避免泄露跨项目存在性。
- 公开服务自行校验权限与业务不变量；HTTP/RPC/MCP 只解析可信身份、解码并调用。公共输入不接受请求自报的管理员、所有者或环境归属。
- 破坏性合同变更同步更新本产品所有调用方和测试，不为旧 Demo 双轨运行。已部署的新产品升级另按版本、备份和发布规范处理。

## 前端代码与状态

- 页面负责路由及组合，业务状态放所属功能模块；基础 UI 不请求业务接口。共享层仅承载稳定通用能力，避免不断扩张的 `utils`、万能页面或跨模块全局 Store。模块间通过公开业务接口和路由上下文协作，不导入另一页面的内部 Hook 或 Store。
- 请求适配集中在所属功能的数据访问边界，统一使用现有客户端和错误合同；组件不散落地址、鉴权头与重试规则。表单到 DTO 的转换在明确边界完成，展示字段不成为新的业务数据来源。
- 在模块路由和适当独立面板设置原生错误边界与加载边界，保留公共导航和无关区域。异步请求、订阅和事件处理器的失败须显式处理，不能误以为渲染错误边界能捕获所有异常。重试只恢复相应区域，不重建整个应用。
- 区分 URL 导航状态、服务端数据、当前表单草稿和用户外观偏好。服务端数据通过已有查询/订阅层读取；不在多个组件各自缓存同一份可修改业务实体。
- 查询键、订阅和缓存身份包含用户、项目、环境、固定版本及必要资源标识。登出、撤权和切项目清理相应可访问数据，迟到请求不能覆盖新上下文；能取消则取消，否则按请求身份丢弃。
- 只从服务端 capabilities 决定可操作呈现；按钮显隐不代替后端校验。错误、空数据、离线、加载和权限不足分别表达，不能都当作空列表。
- 表单复用原生组件和共享校验合同；离开未保存表单应保留草稿或按需求提示。提交过程中防重复，版本冲突明确反馈，不静默覆盖。仅对可回滚、语义明确的操作采用乐观更新。
- 异步业务使用显式可穷尽状态或原生状态模型；不使用互相矛盾的一组布尔值，不新增和 T3 并行的轮次/队列状态。轮询、订阅、计时器和对象 URL 在所属生命周期释放。
- 列表默认分页/有界读取，长列表复用原生虚拟化；大文件预览和日志增量按现有机制加载，禁止每次事件全量刷新全部页面。性能改动用代表性数据和实际测量判断。
- 可访问性包括语义、可见焦点、键盘、输入法、对比度与粗指针触区；自动检查和真实操作互补。可视与布局细则只在 T3 UI 规范维护。

## 测试与质量门禁

| 层次 | 应证明的内容 |
| --- | --- |
| 类型与模块边界 | 严格类型、公共入口、依赖方向、循环和未解析依赖；新增业务代码必须处于检查范围 |
| 领域与合同 | 业务不变量、边界输入、角色组合、范围匹配、状态转换、未知枚举及冲突 |
| 持久化与服务 | 真实临时 SQLite、约束、回滚、并发、升级、重启后读取、权限与必要审计原子性 |
| API 集成 | 可信登录身份、直接越权请求、CSRF/来源、错误合同、撤权、完整成功与失败路径 |
| 前端交互 | 实际入口、路由与缓存隔离、弹窗焦点、键盘、长文本、流式阅读状态和主题/尺寸 |
| 外部集成 | 使用可控替身验证协议和失败语义，再在已授权环境验证真实接入；二者分别报告 |

- 测试断言可观察行为和业务不变量，不能只断言自己的常量或源代码包含某字符串。模块边界可用静态分析，不能拿静态分析代替授权测试。
- 时钟、随机标识和外部连接在确有测试需求的边界注入；用条件等待替代固定长时间 sleep。临时目录在测试结束清理，真实环境测试显式区分。
- 统一质量命令是本地和 CI 的同一个入口；门禁包括格式、类型、依赖边界和相关测试。每次增加模块或入口同步纳入，不允许只检查旧前端却声称全仓检查通过。
- 静态门禁核对实际扫描范围，并保留能触发违规的负向样例；零扫描、漏扫或解析器不兼容必须失败。测试发现覆盖本批实际维护的模块及测试目录，既有、新增和迁入代码均须纳入，不能只扫描新目录或手列旧测试而漏掉其他受影响代码。
- 不用覆盖率数字代替关键风险用例；权限、持久化、任务恢复和合同的负向用例优先。外部服务不可达时明确未验证，不能返回演示结果作为成功。

## 现有模块优化完成条件

第二步只整理当前分支已有能力。每批选一个模块或一条必要的跨模块链路，先记录入口、关键操作、数据来源与已知缺陷，再改变结构；不重新调查 main，不把原计划的未实现功能列为本批必做。

| 完成条件 | 必须提供的证据 |
| --- | --- |
| 功能与流程保留 | 现有入口及成功、失败、恢复路径有对应回归；不能通过删入口、吞异常或模拟成功让检查通过 |
| 职责与依赖清楚 | 所有权和公开能力已说明，调用方已切换；边界检查覆盖新增代码，非法导入反例会失败 |
| 权限一致 | 直接 API、文件/日志及涉及的工具、任务入口使用同一裁决；至少覆盖本批相关的越权与撤权场景 |
| 故障被限制 | 模拟该模块的超时、异常或离线，验证无关模块仍可查询/操作；共享依赖失败按后端规范拒绝相关操作 |
| 前端可维护 | 如涉及 UI，验证上下文切换、请求迟到、局部错误、公共壳及 T3 呈现；不能只交截图或只过类型检查 |
| 交付可追溯 | 列明实际运行的检查及范围、剩余基线缺陷、未测项；删除本批已替代且无调用的代码，更新必要说明 |

改变公共合同、权限或共享基础设施时，验证直接受影响的调用方和代表性跨模块链路；普通局部变更不强制重复全部昂贵测试；仍须运行仓库既有必跑门禁，缩小额外回归范围须说明未受影响的依据。业务错误和已知基线缺陷单独记录，不能把规范目标描述成已经实现。完整优化完成前，不以新增功能抵消未完成的边界整理。

## 规范与决策维护

- 规则使用“必须/禁止”表达硬约束，“优先”表达有理由可调整的选择；区分已确认业务规则、目标结构、当前事实、历史记录和待决定事项。当前事实不得由文件名或愿景推断。
- 影响数据所有权、权限、合同、技术选型或故障边界的决定，在所属规范或模块说明写明原因、选择与影响；局部实现选择无需另建大份决策文档。
- 规范通过一次定稿建立可执行基线，以后随明确需求修订，不把“所有未来需求都设计完”作为开发前提。规范变更同时清理冲突段落，阶段状态只维护在开发文档。
- AI 交接记录当前分支/提交、实际改动范围、已运行命令、未测项和下一步；保留其他任务的改动。只有真正缺失且影响业务权限、数据或范围的决定才询问用户，不重复询问已确认约束。

## 配置、依赖与维护成本

- 环境配置在启动边界统一解析并校验，业务层注入已验证配置；核心配置错误阻止启动，模块配置按后端规范的启用与依赖边界处理。开发、测试、运行数据隔离，启动命令清楚标明目标，不能隐式接入用户真实数据库。
- 优先使用已有包、Node 标准库及锁定上游；新增开源依赖记录用途、固定版本、许可证、维护/运行条件和不用现有实现的原因。正常安装使用冻结锁文件，不顺手升级全树依赖。
- 上游 T3 的适配集中在宿主和业务边界，新增修改须说明是否属于中文化、权限、运行环境或公共框架；不能靠安装目录补丁维持产品。升级需验证平台、客户宿主及协议读取路径。
- 日志用结构化事件、请求/任务关联标识和稳定错误码；只记录允许的上下文，不输出请求正文、密码、会话令牌或文件原文。诊断接口同样受权限控制。
- 引入新模块须说明数据所有者、公开服务、依赖、授权动作、资源范围、入口注册、启停和失败行为；没有页面的能力不增加空菜单。未闭环能力不进入正式功能注册表。
- 关键接口、持久状态、外部动作应能从日志和审计定位“谁、范围、动作、对象、结果”；日志、审计、业务任务分别承担诊断、追责和执行职责，不能相互替代。
