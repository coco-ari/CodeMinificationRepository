# 工程与 AI 协作规范

与 [项目入口](../AGENTS.md)、[后端规范](backend-standard.md)、[T3 UI 规范](t3-ui-standard.md)共同约束当前分支的维护、模块优化与后续开发。这里只维护跨模块工程方法和前端代码组织，不重复业务字段与 UI 尺寸。

修改前的影响分析、缺陷复现与定位、最小改动及相关单测执行，统一遵循全局“现有功能修改与缺陷修复”；当前开发验证按[开发测试规范](development-test-standard.md)提供直接证据。小修已有充分复现、定位和定向回归时，不为凑数编造两个假设、三类收益或重复整站步骤与次数；证据不足则继续定位，不凭猜测修改。本文件只补项目方法与测试范围。

## 面向 AI 的开发流程

1. 先确认业务所有者、公开合同及唯一数据/状态来源；注明当前事实、目标规则和未决问题，不凭文件名或旧方案推断已实现能力。
2. 把任务拆成可运行的纵向切片：合同 → 应用/领域 → 持久化与权限 → 入口 → 必要界面 → 验收。每个切片有具体触发、结果、失败路径和退出条件，按下节从用户任务确定预期行为，不能仅从已有实现反推需求。
3. 开源调研与采用执行全局同名规则；不熟悉的功能先检索、筛选并比较同类项目，再决定实现。项目已有组件和锁定上游继续按所属规范使用；抽象只为已经出现的共同规则服务，不为未来想象的模块建立通用 CRUD、万能仓储、工作流引擎或插件解释器。
4. 先确认接口与状态所有权再改调用方；一个值有一个权威来源。不要分别给 HTTP、MCP、页面和后台修出四份不同业务规则。
5. 遇到失败先判断是本次缺陷、基线失败还是环境限制；保留证据并修正原因。不能通过跳过测试、降低类型严格度、吞异常或加入假成功回退完成任务。
6. 交付说明行为变化、使用入口、验证结果与未覆盖项。普通任务不生成大型过程文档；跨会话只记录必要决策、剩余工作和可复现命令。

### 用户任务与连续使用验收

- **修改前写清使用结果**：在现有任务或验收清单中，用简短场景说明用户、初始状态、目标和可观察结果。按本次影响判断更新资料、刷新页面、断网恢复、再次操作或重进旧会话后的预期；选择直接相关的场景，不默认穷举。已确认规则与这些结果冲突时，先指出冲突并按用户最新决策修订，不能以“符合旧文档”为由关闭问题，也不能擅改业务规则。
- **实现时限制用户负担和影响范围**：每增加一个用户步骤，说明它承担的输入、选择、授权或确认责任；系统能够安全完成的查询、关联和状态恢复不转交用户。具体恢复呈现遵循 [UI 操作简洁性](t3-ui-standard.md#操作简洁性)。阻塞、重试、加载和缓存失效限制在真实依赖范围内，不能因一个对象异常拖住无关项目或操作；跨范围限制须有明确的共享依赖或业务不变量依据，不为简化而放宽授权或丢弃未确认请求。
- **验收时验证连续使用**：涉及状态、数据生命周期或交互流程的变更，至少覆盖一个直接受影响的连续场景，如“首次使用 → 更新或中断 → 恢复后再次使用”，检查任务能否继续、已有内容是否稳定、无关操作是否仍可用。预期来自用户目标及公开合同，不能只断言按钮可点、参数已传或接口返回成功。相关自动化与真实验收按下方门禁分层记录；纯静态文案且无流程影响时不强加此类测试。
- **批次结束复审流程**：复用已有步骤对比及测试证据，从使用者角度检查是否出现无理由的额外步骤、内部术语、重复加载、无关阻塞或恢复死路。代码审查发现、已复现缺陷和已验证修复分别标注，不把推测当成线上故障。该检查纳入现有批次收尾，不要求新增 Agent、独立长报告或逐项用户审批，不重复已有充分证据且未受影响的测试，也不扩大为整站重构。

## 模块说明与依赖组织

每个实际模块只维护一份简短说明，可放在模块 README 或现有入口文档。写清下列内容，并链接代码合同及测试；不手抄每个字段，也不为未实现能力创建空模块。

| 项目 | 必须说清的内容 |
| --- | --- |
| 职责 | 本模块负责什么、不负责什么；当前功能入口及调用方 |
| 数据与状态 | 自有表、文件元数据、缓存及任务状态；引用其他模块的标识 |
| 公开能力 | 公开入口、输入输出合同、业务错误；内部文件不对外承诺 |
| 依赖 | 允许依赖的模块和具体用途；装配位置；同步调用或异步通知的理由 |
| 权限 | 动作标识、资源真实归属、私有/共享限制、撤权处理；链接同源动作合同与权限用例 |
| 运行与验证 | 配置、初始化/关闭、资源预算、失败影响范围；成功、越权与故障的验证入口 |

- 后端沿用现有 `autoops/server/modules/<模块>` 的公开入口模式；前端在当前 T3 宿主内按业务功能组织，不另建应用或页面壳。现有目录是否迁移，在第二步按调用关系确定，不一次批量搬动全仓。
- 模块内部按需要拆入口、用例、领域和基础设施；小模块可以少文件，不建立空层。文件划分依据职责与变化原因，不用固定行数迫使简单逻辑碎片化。
- 公共合同只含可共享的 Schema、DTO、动作与错误语义，不导入服务端运行时。前端不能导入服务端存储、凭证或执行器；后端不能依赖页面组件。
- 依赖方向为入口调用应用服务，应用服务使用领域规则及注入端口，基础设施实现端口，组合根负责装配。组合根不写业务规则，也不发展成万能路由/服务文件；入口按所属模块组织。
- 跨模块只使用公开能力；出现双向依赖时，先核对职责，把跨模块用例放到明确的协调位置，通过公开端口装配。不以动态导入、全局事件总线或服务定位器绕过边界检查。
- 平台共享层仅提供配置、连接、事务、日志等机制，不导入业务模块。一个模块独用的辅助代码留在本模块；提取共享代码须有真实调用者和共同语义，禁止以 `common/utils` 收纳难归属的业务逻辑。
- 发现循环必须消除，不因补写说明而获准保留；变更所有权时先更新依赖说明、合同及受影响调用方，再改实现。自动边界检查需包含类型导入、路径别名与新增目录；检查未覆盖的目录必须明确列出，不能声称全仓受控。

模块门禁根据已确定的数据所有者和公开入口保护内部实现，同时允许必要业务依赖。每个新增边界至少有合法调用通过及非法穿透失败的解析用例，覆盖类型、别名或动态导入等实际用法。检查范围扩大后重新核对遗漏路径；不能用“没有循环”替代公开接口检查，也不能只检查示例目录。

## 模块与合同

- 模块公开入口只导出明确服务、DTO 和注入端口，内部实现不成为隐式 API。依赖方向由自动检查约束；领域层不得依赖 HTTP、数据库驱动、前端或 T3 内部代码。
- 运行时输入校验与 TypeScript 类型同源；优先沿用 T3 已使用的 Effect Schema。公开 DTO 与数据库行分离，禁止把数据库对象、凭证明文或第三方完整响应直接返回客户端。
- 动作、错误码、资源身份和 API 合同在公共合同中定义；前后端不手抄枚举、重新解释角色或拼接隐藏协议。时间使用明确时区的时间戳，字节、持续时间等字段标明单位；金额等精确值不使用含糊浮点数。
- 输入使用允许字段集合，明确空值、缺省、长度、分页、排序和大小上限；未知资源与无权限按统一策略返回，避免泄露跨项目存在性。
- 公开服务自行校验权限与业务不变量；HTTP/RPC/MCP 只解析可信身份、解码并调用。公共输入不接受请求自报的管理员、所有者或环境归属。
- 破坏性合同变更同步更新本产品所有调用方和测试，不为旧 Demo 双轨运行。正式启用或生产环境升级另按版本、备份和发布规范处理；当前开发测试实例遵循[后端数据策略](backend-standard.md#复用与运行架构)。

## 前端代码与状态

- 页面负责路由及组合，业务状态放所属功能模块；基础 UI 不请求业务接口。共享层仅承载稳定通用能力，避免不断扩张的 `utils`、万能页面或跨模块全局 Store。模块间通过公开业务接口和路由上下文协作，不导入另一页面的内部 Hook 或 Store。
- 请求适配集中在所属功能的数据访问边界，统一使用现有客户端和错误合同；组件不散落地址、鉴权头与重试规则。表单到 DTO 的转换在明确边界完成，展示字段不成为新的业务数据来源。
- 在模块路由和适当独立面板设置原生错误边界与加载边界，保留公共导航和无关区域。异步请求、订阅和事件处理器的失败须显式处理，不能误以为渲染错误边界能捕获所有异常。重试只恢复相应区域，不重建整个应用。
- 区分 URL 导航状态、服务端数据、当前表单草稿和用户外观偏好。服务端数据通过已有查询/订阅层读取；不在多个组件各自缓存同一份可修改业务实体。
- 查询键、订阅和缓存身份包含用户、项目、环境、资料范围、当前内容修订或本轮固定输入及必要资源标识。登出、撤权和切项目清理相应可访问数据，迟到请求不能覆盖新上下文；能取消则取消，否则按请求身份丢弃。
- 只从服务端 capabilities 决定可操作呈现；按钮显隐不代替后端校验。错误、空数据、离线、加载和权限不足分别表达，不能都当作空列表。
- 表单复用原生组件和共享校验合同；离开未保存表单应保留草稿或按需求提示。提交过程中防重复，版本冲突明确反馈，不静默覆盖。仅对可回滚、语义明确的操作采用乐观更新。
- 异步业务使用显式可穷尽状态或原生状态模型；不使用互相矛盾的一组布尔值，不新增和 T3 并行的轮次/队列状态。轮询、订阅、计时器和对象 URL 在所属生命周期释放。
- 列表默认分页/有界读取，长列表复用原生虚拟化；大文件预览和日志增量按现有机制加载，禁止每次事件全量刷新全部页面。性能改动用代表性数据和实际测量判断。
- 可访问性包括语义、可见焦点、键盘、输入法、对比度与粗指针触区；自动检查和真实操作互补。可视与布局细则只在 T3 UI 规范维护。

## 测试与质量门禁

| 层次 | 应证明的内容 |
| --- | --- |
| 类型与模块边界 | 严格类型、公共入口、依赖方向、循环和未解析依赖；新增业务代码必须处于检查范围 |
| 领域与合同 | 业务不变量、边界输入、角色组合、范围匹配、状态转换、未知枚举及冲突 |
| 持久化与服务 | 真实临时 SQLite、约束、回滚、并发、升级、重启后读取、权限与必要审计原子性 |
| API 集成 | 可信登录身份、直接越权请求、CSRF/来源、错误合同、撤权、完整成功与失败路径 |
| 前端交互 | 实际入口、路由与缓存隔离、弹窗焦点、键盘、长文本、流式阅读状态和主题/尺寸 |
| 外部集成 | 使用可控替身验证协议和失败语义，再在已授权环境验证真实接入；二者分别报告 |

- 新增行为以针对性用例保护关键不变量，断言可观察结果，不能只断言自己的常量、源码字符串或实现细节。纯文案/样式无行为变化时仍执行相关回归与 T3 UI 验收，不编造镜像单测。模块边界可用静态分析，不能拿静态分析代替授权测试。
- 统一质量命令使用仓库现有本地入口；当前开发不等待 GitHub CI。按影响完成必要的格式、类型、构建、依赖边界及定向测试，每次增加模块或入口同步纳入，不允许只检查旧前端却声称全仓检查通过。
- 静态门禁核对实际扫描范围，并保留能触发违规的负向样例；零扫描、漏扫或解析器不兼容必须失败。测试发现覆盖本批实际维护的模块及测试目录，既有、新增和迁入代码均须纳入，不能只扫描新目录或手列旧测试而漏掉其他受影响代码。
- 不用覆盖率数字代替关键风险用例；权限、持久化、任务恢复和合同的负向用例优先。外部服务不可达时明确未验证，不能返回演示结果作为成功。

以下四项约束验证方法，不改变用户已确认的交付范围、执行顺序、授权和完成标准。已有充分证据且未受影响的步骤不因规范补充而重做；阶段性汇报后继续尚未完成且可执行的事项，不以整理规范或优化验收工具替代业务交付。

### 尽早验证最小真实链路

- 修改第三方集成、运行器、跨进程、跨依赖实例或容器边界时，先核对锁定版本的实际合同；必要的本地验证通过后，尽早使用正式构建产物、真实执行身份和代表性输入，验证最小完整调用及最相关的拒绝或恢复路径，再扩展验收矩阵。不把首次真实兼容性检查推迟到整站切换后。
- 模型回答、HTTP 成功、命令接收、ACK、状态投影和业务终态分别判断；涉及工具调用时核对实际工具结果，涉及持久化或恢复时核对权威收据与最终状态。
- 真实验证只在已授权的隔离环境执行；缺少条件时保留证据缺口并推进不受影响的工作，不将替身结果计为真实通过，也不重复验证未受影响的边界。

### 验收工具遵循正式合同

- 测试、探针、恢复脚本和部署检查优先复用所属模块的公开解码器、类型及状态判定；测试预期来自业务要求和可观察结果，不能仅用同一实现自证正确。无法复用时，标明合同版本，并用代表性的真实成功、预期拒绝和恢复样本校准判断。
- 按具体接口核对状态码、可空及可选字段、异步结果、身份和标识范围、幂等键及错误恢复语义，禁止把其他接口的成功码、必填字段或本地记录数直接套用。结构化对象按合同语义比较，签名、源码包、附件等仍按要求核对原始字节；模型回答核对事实与实际执行结果，仅在需求规定格式时要求固定措辞。
- 验收器误判时保留原失败，优先只读复验同一结果；执行结果未知时沿原请求核对，不为获得通过结果而重复上传、调用模型、发布或创建业务对象，不修改正确产品去迎合错误断言。

### 先稳定代表性用例再展开矩阵

- UI 自动化固定角色、权限、初始数据、视口、主题及必要的字体和输入条件；使用语义入口，同名控件限定所属区域，不依赖偶然文本拼接或 DOM 位置。时钟、随机标识和外部连接只在确有测试需求的边界注入，临时目录在结束后清理。
- 等待可观察的响应、状态和焦点转换，使用与操作合同一致的有界等待，禁止用固定长时间 sleep 替代。捕获响应或注入故障前先建立监听，核对方法、地址、原请求标识和运行状态，不能把准备请求当成实际任务已接受。
- 共同入口、等待逻辑或证据采集改变后，先跑代表性成功及受影响的失败恢复用例，再扩大角色、主题和尺寸矩阵。出现共同原因失败时先修复该原因，暂停依赖它的矩阵扩展，继续其他独立事项；不能据此删减最终必需覆盖。
- 按实际风险组合验收维度，不默认穷举角色、主题、尺寸与网络状态的全部组合。权限重点覆盖角色、项目、环境及撤权；布局重点覆盖主题、尺寸、长内容和滚动；公共组件选择直接调用方的代表性页面。确有交互风险的组合及用户明确约定场景必须覆盖，已有有效证据按下节复用，在原清单注明覆盖关系，不另建重复矩阵。

### 固定候选并复用有效证据

- 必要的本地检查返回并通过后再冻结候选；当前开发不以 GitHub CI 为等待条件。工作树有其他任务改动时，从固定提交构建并核对源码、依赖、配置及产物来源，部署后核对实际健康和受影响功能。
- 验证证据记录提交或产物、环境、相关配置、用例范围及结果。按下表选择本地验证；复用证据须说明未受影响的依据，代码、依赖、环境、关键配置变化或出现证据缺口时重新确定范围。本表不授权跳过当前适用的本地质量与功能门禁，也不把模拟通过计为真实业务通过；其他环境的 CI 要求按其发布规则执行。
- 当前 AutoOps 开发测试数据可按需重建，范围遵循[后端数据策略](backend-standard.md#复用与运行架构)。历史账号、会话、全表全文件、原 CLI 身份与账本及认证窗口的全量保留检查不再作为当前开发发版前置；已有结果保留为历史证据。仍须固定候选、核对源码和产物、完成必要的本地检查、构建与实际健康检查，并验证本批实际影响的权限、生命周期、失败及恢复流程。重建后按新夹具的真实状态验收，不把旧实例结果冒充新实例已通过，也不为恢复历史门禁扩建验收工具。
- 独立审查先检查改动和已有证据，再对高风险或有缺口的部分复验；重复整套测试应说明新增验证目标，不将更换 Agent 自动视为重跑理由。

| 改动类型                           | 本地验证范围                                                                                              |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 纯文档，无可执行内容或运行配置变化 | 差分、链接和约束一致性检查；不因文档提交重跑无关业务测试。命令、脚本示例或配置变化需另验其实际影响        |
| 局部实现或页面                     | 相关单测、合同和受影响的成功、失败及恢复交互；页面按 UI 规范核对对应呈现与操作步骤                        |
| 公共合同、权限、持久化或共享组件   | 验证直接受影响调用方及代表性跨模块链路，包含相关负例；持久化另验真实初始化、重复执行及恢复                |
| 当前开发发行候选                   | 从固定提交构建，核对产物及必要本地检查，验证实际健康及本批真实业务；未变化且条件仍成立的证据可复用         |

## 现有模块优化完成条件

第二步只整理当前分支已有能力。每批选一个模块或一条必要的跨模块链路，先记录入口、关键操作、数据来源与已知缺陷，再改变结构；不重新调查 main，不把原计划的未实现功能列为本批必做。

| 完成条件 | 必须提供的证据 |
| --- | --- |
| 功能与流程保留 | 现有入口及成功、失败、恢复路径有对应回归；不能通过删入口、吞异常或模拟成功让检查通过 |
| 职责与依赖清楚 | 所有权和公开能力已说明，调用方已切换；边界检查覆盖新增代码，非法导入反例会失败 |
| 权限一致 | 直接 API、文件/日志及涉及的工具、任务入口使用同一裁决；至少覆盖本批相关的越权与撤权场景 |
| 故障被限制 | 模拟该模块的超时、异常或离线，验证无关模块仍可查询/操作；共享依赖失败按后端规范拒绝相关操作 |
| 前端可维护 | 如涉及 UI，验证上下文切换、请求迟到、局部错误、公共壳及 T3 呈现；不能只交截图或只过类型检查 |
| 交付可追溯 | 列明实际运行的检查及范围、剩余基线缺陷、未测项；删除本批已替代且无调用的代码，更新必要说明 |

回归范围与证据复用按上方测试门禁执行。业务错误和已知基线缺陷单独记录，不能把规范目标描述成已经实现。完整优化完成前，不以新增功能抵消未完成的边界整理。

收尾时在现有运行模块说明中维护一张逐模块验收表，记录本批状态、公开交集、相关行为测试及未验证范围，不为此复制接口字段。已实现功能、未接入的独立切片和未来需求分别标识。只有对应缺口有实现和验证证据才能关闭；测试数量、文件搬迁量或一次部署成功不表示全模块完成。范围限定为现有能力的职责、接口和生命周期，不把多实例、全面换库或新业务作为默认前提。

## 规范与决策维护

- 规则使用“必须/禁止”表达硬约束，“优先”表达有理由可调整的选择；区分已确认业务规则、目标结构、当前事实、历史记录和待决定事项。当前事实不得由文件名或愿景推断。
- 影响数据所有权、权限、合同、技术选型或故障边界的决定，在所属规范或模块说明写明原因、选择与影响；局部实现选择无需另建大份决策文档。
- 规范基线随明确需求修订，不把“所有未来需求都设计完”作为开发前提。规则变化时改写所属条款及冲突引用，不在入口另加一套重复规定；历史决定注明适用时间，不能继续使用无范围的“当前”“本轮”指挥现行任务。
- 当前交付清单只保留同一子项的代码、自动测试、部署、真实验收状态，以及关键证据链接、剩余问题和下一步；不适用项说明原因。完整失败、修复及历次发行过程留在相应证据或历史记录，保留可追溯性，不持续追加到当前状态单元格。其他文档引用该清单，不另维护第二份完成结论。
- AI 交接记录当前分支/提交、实际改动范围、已运行命令、未测项和下一步；保留其他任务的改动。只有真正缺失且影响业务权限、数据或范围的决定才询问用户，不重复询问已确认约束。

## 配置、依赖与维护成本

- 环境配置在启动边界统一解析并校验，业务层注入已验证配置；核心配置错误阻止启动，模块配置按后端规范的启用与依赖边界处理。开发、测试、运行数据隔离，启动命令清楚标明目标，不能隐式接入用户真实数据库。
- 使用已有包、Node 标准库及锁定上游；新增开源候选按全局“开源调研与采用”筛选，实际引入时记录用途、固定版本、许可证、维护/运行条件和不用现有实现的原因。正常安装使用冻结锁文件，不顺手升级全树依赖。
- 上游 T3 的适配集中在宿主和业务边界，新增修改须说明是否属于中文化、权限、运行环境或公共框架；不能靠安装目录补丁维持产品。升级需验证平台、客户宿主及协议读取路径。
- 日志用结构化事件、请求/任务关联标识和稳定错误码；只记录允许的上下文，不输出请求正文、密码、会话令牌或文件原文。诊断接口同样受权限控制。
- 引入新模块须说明数据所有者、公开服务、依赖、授权动作、资源范围、入口注册、启停和失败行为；没有页面的能力不增加空菜单。未闭环能力不进入正式功能注册表。
- 关键接口、持久状态、外部动作应能从日志和审计定位“谁、范围、动作、对象、结果”；日志、审计、业务任务分别承担诊断、追责和执行职责，不能相互替代。
