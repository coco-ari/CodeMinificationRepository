# Java 服务部署操作手册

适用版本：2026-10-15 项目工作空间版。此手册对应当前已部署的控制台，优先说明已有 A / B 环境如何使用。密码、下载密钥和 Agent 接入口令不写入手册。

## 明天第一次试用：发布一个 API 服务

1. 打开 [交付控制台](https://bst-tmp.996788.xyz)，使用已有管理员账号登录。用户名是 **`admin`**。
2. 进入 **越南 SOL 标准版**，顶部环境选择 **Agent 验证**。也可直接打开 [验证环境的部署发布页](https://bst-tmp.996788.xyz/#/projects/bf24f60e-f0ad-4f15-8520-b93d112f65b0/deployments?environment=2fb57ec7-e8d0-4fa1-b919-48b210bbd0e6)。
3. 在「服务器」确认 A 在线；回到「部署发布」，找到 **brezze-api**。已有仓库、分支、构建、端口、网络和健康检查配置，无需重新安装 Agent 或重新创建服务。
4. 点击 **更新**，核对项目、环境、服务、仓库、分支和服务器后确认。这个按钮会创建一个完整发布任务，中心会重新检查远端分支最新提交；不是仅启动上次的容器。
5. 进入 **发布记录 → 查看详情**，等待“发布成功”。查看完整 commit、各阶段耗时和日志。可以刷新或收藏当前任务地址，关闭页面不会取消任务。
6. 在 A 上执行下面的只读检查，应返回包含 `swaggerVersion` 的 JSON。初次试用先只发布 API，便于观察资源占用和流程。

```bash
curl --fail --max-time 15 http://127.0.0.1:20111/api/swagger-resources
```

本次验收后四个 Agent 验证副本已主动停止，故首次进入时看到“已停止”或健康“异常”是预期状态；点击发布会创建/启动该目标容器。历史记录中有一次故意制造的健康检查失败及自动回退，用于验收，不代表当前有未完成故障。

**当前试用是并行发布。** 原“测试环境”的四个目标是 Jenkins 容器的只读观察记录；原域名和 Nginx 仍然转发到 Jenkins 容器。Agent 验证端口仅监听 A 的 localhost，不会替换原 URL 的服务，也不能直接用 `公网IP:20111` 访问。

如需从自己的电脑测试健康地址，可在电脑终端建立临时 SSH 转发，再打开 localhost 地址：

```bash
ssh -N -L 20111:127.0.0.1:20111 root@129.226.133.152
# 另一个终端执行，结束时在上面的 SSH 终端按 Ctrl+C：
curl --fail http://127.0.0.1:20111/api/swagger-resources
```

## 本次已配置的四个服务

| 服务 / Maven 模块 | Agent 验证端口 | 原 Jenkins 端口 | 健康检查路径 |
| --- | --- | --- | --- |
| `brezze-api` | `127.0.0.1:20111` | `127.0.0.1:10111` | `/api/swagger-resources` |
| `brezze-communication` | `127.0.0.1:20110` | `127.0.0.1:10110` | `/communication/swagger-resources` |
| `brezze-manage` | `127.0.0.1:20112` | `127.0.0.1:10112` | `/manage/swagger-resources` |
| `brezze-reward` | `127.0.0.1:20115` | `127.0.0.1:10115` | `/reward/swagger-resources` |

四个服务来自同一 Gitee 仓库的独立 Maven 模块，当前发布分支为 `p-vi-sol`，共用 Docker 网络 `test-middleware` 和现有测试中间件。每次发布只更新所选目标。API 的完整业务功能还依赖其他服务，单独启动 API 后只验 HTTP 就绪，不能据此判断所有业务流程均可用。

验收时固定的提交为 `dc1420de0ba15319bffaa5a413dfc8f17dda8892`。明天若分支有新提交，“更新”应显示新的 commit；不要求始终与本手册的验收提交相同。

API、manage、reward 的服务间调用已在验证目标的应用参数中覆盖为对应 Agent 容器的 Docker DNS 地址。不要改回 `127.0.0.1`，该地址在容器内指向自己。communication 保留 `--ybt.enable=false`。原 Jenkins 配置没有随本次验证修改。

## 发布过程中中心和 Agent 分别做什么

| 页面阶段 | 执行位置 | 实际动作 |
| --- | --- | --- |
| 准备源码 | B 中心 | 按任务创建时固定的仓库和分支拉取代码，确定 commit，生成并固定 ZIP 和 SHA-256 |
| 排队 | B 中心 | 等待 A 空闲，同服务器所有项目串行执行 |
| 下载源码 | A Agent | 下载本任务固定 ZIP，校验摘要与解压路径 |
| 编译打包 | A 临时构建容器 | 使用 Maven/JDK 镜像编译所选模块及依赖，生成 JAR 和业务镜像 |
| 更新容器 | A Agent | 使用本次固定运行配置更新该目标容器 |
| 健康检查 | A Agent | 等待约定 HTTP 状态与响应内容，成功后保存版本；失败时尝试恢复上次成功版本 |

服务器只需 Docker 等接入依赖，无需在宿主机安装 JDK 或 Maven。编译容器完成后会清理，目标的 Maven 依赖缓存可复用。中心和 Agent 的日志、阶段时间及成功版本分别持久保存。

新任务在中心侧分别显示拉取代码、固定提交和打包 ZIP。Agent 1.2.0 分别显示编译与镜像耗时；A 当前的旧 Agent 继续合并显示编译 / 镜像。历史任务保留实际记录的阶段，不虚构子步骤耗时。

## 更新代码、切换分支和回退

- **更新到最新代码**：直接点击目标的「更新」。每个新任务会重新检查远端；上游失败时报告失败，不会静默使用旧包。无需先在仓库页同步一次。
- **只同步下载仓库**：「代码仓库 → 立即同步」检查仓库的默认下载分支，供浏览器/Jenkins 使用。它不发布服务，也不改变环境的发布分支。
- **切换发布分支**：在「环境与服务」选择环境和服务，点击「配置当前环境源码」，选择仓库并填写分支；保存后创建新发布任务。同环境同服务的多台服务器共用该源码选择。
- **回退已发布版本**：在「部署发布」点击目标的「回退版本」，选择成功版本并确认。恢复该版本的镜像和当时运行配置，再做健康检查，不重新编译。每个目标保留最近五个成功版本以及当前恢复基线。
- **重启当前版本**：点击「重启」，沿用当前成功版本，不拉取新代码。

已创建任务的仓库、分支和配置不会随之后编辑而改变。手动回退也不会把编辑表单中的最新配置改回历史值；下一次“更新”会使用表单中保存的当前配置。

发布工作台的“更新代码”会拉取当前环境分支最近 100 条提交，可以选择其中某个 commit 发布。选择“最新代码”则在任务准备时再次获取最新提交；“已发布版本”用于回退保留的成功版本。原 Jenkins 下载接口仍只使用仓库的默认下载分支。

## 新项目从零配置

1. **项目首页 → 创建项目**：自动生成“测试”“生产”两个空环境，默认进入测试。
2. **代码仓库 → 添加仓库**：填写 Gitee HTTPS 地址、默认下载分支，选择已有凭证或新增凭证。私有仓库需要有效的只读 Git 凭证。
3. **服务器 → 绑定已接入服务器**：使用现有 Agent，无需重复安装。新增服务器时使用「接入新服务器」，在对应 Linux 服务器执行生成命令，等待在线。共享服务器的 CPU/内存/磁盘是整机指标。
4. **环境与服务 → 新增服务**：类型选 Java，填写 Maven 模块；单模块项目可填 `.`。在当前环境为该服务配置仓库及分支。
5. **部署发布 → 新增部署目标**：选择服务、已绑定服务器和「平台管理」，配置构建/运行/健康检查后保存。
6. **更新**：检查确认信息并发布。一个项目可以有多个仓库；不同服务可以选择不同仓库或同仓库不同模块。

现有 Agent 若是仅观察，可在「系统管理 → 服务器总览」启用平台部署，再创建新的平台管理目标。原观察目标仍保持只读，不能直接改为接管原 Jenkins 容器。存在未完成任务时不能切换服务器管理方式。

### Java 配置怎么填写

| 配置 | 含义和本环境示例 |
| --- | --- |
| Maven 模块 / JAR 路径 | `brezze-api` / `brezze-api/target/*.jar`；必须匹配唯一 JAR |
| 构建镜像 | `maven:3.9.9-eclipse-temurin-8`，其中包含 Maven 和 JDK 8 |
| 运行镜像 | 本环境沿用相同 Maven 镜像以匹配 Jenkins；新项目可使用匹配 Java 版本的 JRE 镜像 |
| 构建资源 | API/manage/reward：1 核、768 MiB；communication：1 核、1024 MiB |
| 运行资源 | 每个验证副本 1 核、512 MiB；JVM 最大堆为 192 MiB |
| Profile | `test`，使用应用原有配置文件 |
| JVM 参数 | `-Xmx...` 等 JVM 启动参数，每行一个；不是 Maven 参数 |
| 应用参数 | Spring 属性覆盖，例如 `--call.manage.path=...`，每行一个 |
| 端口 | 宿主机 `127.0.0.1:20111` 映射容器 `10111`，宿主端口不能冲突 |
| 网络 | 本环境填写已经存在的 `test-middleware`；留空会创建目标自己的平台网络，并非所有服务自动共用网络 |
| 存储 | `logs:/app/logs` 为目标专属命名卷，不能填写任意宿主机目录 |
| 健康检查 | 容器端口 `10111`、路径 `/api/swagger-resources`、状态 `200`、正文包含 `swaggerVersion`；等待 240 秒，每 5 秒检查 |

健康地址由具体服务决定。可以用 `/actuator/health` 或自定义就绪接口，但必须真实可访问。当前 Java 检查支持 HTTP 状态和响应内容，不支持任意 Shell/TCP 检查。Swagger 检查只能证明 HTTP 就绪；涉及数据库、消息与业务流程的验收需要另外执行。

## A 内存紧张时如何让 Jenkins 临时让出资源

A 约 3.5 GiB 内存，原四个 Java 服务和中间件常驻。首次试用先单独发布一个服务。需要运行多个验证副本时，可按已确认的方式暂停 Jenkins 控制器与构建节点；先在 Jenkins 确认没有执行中的构建且队列为空。

以下命令在 **A** 执行，只停止 Jenkins 本身，不停止原四个业务容器：

```bash
docker stop cmr-jenkins-test-agent-1 cmr-jenkins-test-jenkins-1
```

测试结束后，先停止本次启动的验证副本；下列名称是本环境固定的四个 Agent 目标，只需停止实际运行的副本：

```bash
docker stop \
  cmr-93ecd821-c916-480e-8db1-1ed0cbd3cce3 \
  cmr-765e9163-f8ad-4191-9806-589b47dde222 \
  cmr-000acc17-f7cf-4edd-bce6-19e14442c87f \
  cmr-4103a8c2-a1e5-48c6-835b-d245e37de7ea
docker start cmr-jenkins-test-jenkins-1 cmr-jenkins-test-agent-1
docker ps --format 'table {{.Names}}\t{{.Status}}'
```

在 Jenkins 中确认 `docker-builder` 在线，再恢复正常使用。不要删除容器或数据卷，不要重新创建 Jenkins。当前控制台没有“停止服务”按钮，验收结束释放副本内存使用上述 SSH 命令；以后再次点击发布或重启即可运行验证副本。

## 原 Jenkins 主流程如何使用

Jenkins 控制器与构建节点已经恢复，四个原业务容器和中间件保持原状；原 Nginx 的域名、证书与路由未修改。A 实际使用的是宿主机 systemd Nginx。

原四个 `solstandard-*-test` 任务保持原配置：选择对应任务并按原习惯构建。**`DEPLOY=true` 是原任务的默认值**，下载、编译后更新对应 Jenkins 服务；取消勾选则只下载编译。今天的兼容回归为 `solstandard-api-test #4`，`DEPLOY=false`，结果 `SUCCESS`。

Jenkins 继续使用原 SOURCE_URL 和凭据 `solstandard-source-download`；不要重置仓库下载密码、修改默认下载分支或替换 Jenkins 凭据来试用 Agent。Agent 使用自身认证下载固定任务源码，无需在 A 配置 Gitee 密码。

## 遇到问题先看哪里

| 现象 | 操作 |
| --- | --- |
| 服务器失联 | 查看最后心跳，在 A 执行 `docker logs --tail 100 cmr-agent`，检查到中心的 HTTPS 连通性；不要重新安装覆盖身份 |
| 一直排队 | 查看同一服务器是否已有任务运行；同服务器跨项目串行，关闭页面不会取消队列 |
| 准备源码失败 | 检查项目内的仓库、环境分支、Gitee 凭证及 B 到 Gitee 的网络 |
| 编译失败 | 在任务日志查第一条 Maven 错误；检查 JDK 版本、模块、产物路径和依赖镜像源 |
| 镜像下载返回 HTML | 检查 Docker 镜像代理；不要把它误判成仓库或 Maven 错误。可按运维指南预拉取官方镜像 |
| 健康检查失败 | 检查 Profile、端口、路径、依赖服务和启动日志，确认自动回退是否成功 |
| “失败 · 已回退” | 发布没有成功，但已恢复上一成功版本；修正原因后重新发布 |
| 第一次发布失败 | 没有成功基线可恢复，修正配置后重新发布 |
| 原域名仍是旧服务 | 并行验证的正常现象；原域名仍指向 Jenkins，正式切换另行安排 |

完整备份与中心回退见 [运维指南](deployment-guide.md#升级备份与恢复)；本次任务 ID、测试记录和已有问题见 [并行验收记录](parallel-verification-20261015.md) 和 [本版本验收清单](release-checklist-20261015.md)。
